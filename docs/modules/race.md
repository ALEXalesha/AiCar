# race.py

Заезд одного поколения. Физика, чекпоинты, смерть, приспособленность.

Здесь сходится всё: трасса, поле расстояний, машинка, датчики и сеть. Модуль хранит состояние 50 машинок и двигает их шаг за шагом.

## Состояние

Никаких объектов-машинок. Всё поколение это набор массивов длины N.

| Поле | Тип | Смысл |
|---|---|---|
| `pos` | (N, 2) float | позиции |
| `angle` | (N,) float | куда смотрит нос, радианы |
| `speed` | (N,) float | скорость, пикселей в секунду |
| `alive` | (N,) bool | кто ещё едет |
| `cp` | (N,) int | сколько чекпоинтов взято |
| `idle` | (N,) int | шагов без нового чекпоинта |
| `finish_step` | (N,) int | на каком шаге финишировал, -1 если нет |

Такое устройство называется структура массивов, в противоположность массиву структур. Оно менее привычно, но позволяет считать всё поколение целиком без единого цикла по машинкам.

## Один шаг

```
observe()           датчики и скорость -> 8 чисел на машинку
brain.forward()     8 чисел -> руль и газ
_drive()            физика
_take_checkpoints() продвижение по трассе
проверки           кто врезался, кто застоялся, кто финишировал
```

### `observe()`

Семь лучей делятся на `RAY_MAX`, скорость на максимальную скорость машинки. Получается 8 чисел в диапазоне 0..1.

Нормировка сделана здесь, а не в `sensors.py`, потому что именно тут известны обе константы. Датчик должен возвращать пиксели, а как их масштабировать под сеть, решает потребитель.

### `_drive(steer, throttle)`

```
speed += (throttle * accel - speed * DRAG) * DT * live
speed  = clip(speed, 0, max_speed)
angle += steer * max_steer * (speed / max_speed) * DT * live
pos   += [cos(angle), sin(angle)] * speed * DT * live
```

**Про `live`.** Это `alive`, приведённое к числам: 1.0 для живых, 0.0 для мёртвых. Умножение на него замораживает мёртвые машинки без единого `if`. Они остаются лежать там, где врезались, что и нужно для отрисовки: видно место массовых аварий.

**Про множитель `speed / max_speed` в повороте.** Без него стоящая машинка крутилась бы на месте, как танк. Это не только неправдоподобно, но и вредно для обучения: эволюция немедленно нашла бы стратегию "стоять и вращаться", а от неё трудно уйти. Тест `test_a_standing_car_cannot_turn` держит это поведение.

**Про `clip(speed, 0, ...)`.** Нижняя граница ноль означает, что задний ход невозможен. Отрицательный газ это торможение, а не реверс. Так эволюция не может научиться пятиться от старта, набирая расстояние в обратную сторону.

**Про фиксированный `DT`.** Шаг всегда 1/60 секунды, независимо от реального FPS. Иначе на медленной машине физика считалась бы крупнее, и один и тот же seed давал бы разные результаты на разных компьютерах.

### `_take_checkpoints()`

Чекпоинт считается взятым, когда машинка пересекла его плоскость:

```python
ahead = dot(pos - cp_mid[next], cp_dir[next]) >= 0
```

`cp_mid` это точка чекпоинта на центральной линии, `cp_dir` это направление трассы в ней. Скалярное произведение положительно, когда машинка находится по ходу движения дальше этой точки.

**Почему не расстояние до середины чекпоинта.** Первая версия засчитывала чекпоинт, если машинка ближе `CHECKPOINT_RADIUS` к его середине. Такой способ ломается двумя разными способами.

Первый: машинка, идущая вдоль стены, отстоит от середины на половину ширины трассы, то есть на 45 пикселей. При радиусе 45 она не засчитывает вообще ничего и умирает от простоя, хотя едет правильно. А ехать вдоль стены выгодно на внутреннем радиусе поворота, то есть именно там, где хочется, чтобы машинка ехала.

Второй: расстояние между чекпоинтами зависит от длины трассы. При 360 точках и длине 2050 пикселей соседние чекпоинты отстоят на 45.6 пикселя, что почти равно радиусу засчитывания. На трассе покороче машинка на старте оказалась бы сразу внутри зоны следующего чекпоинта и получала бы его даром.

Проверка полуплоскости свободна от обеих проблем. Она не зависит ни от положения по ширине трассы, ни от расстояния между чекпоинтами. Проскочить её тоже нельзя: это не зона, а граница, и пересечь её незаметно невозможно.

Тесты `test_a_car_hugging_the_wall_still_takes_checkpoints` и `test_checkpoints_are_taken_in_order_along_the_track` закрывают оба случая.

Номер чекпоинта только растёт: условие `cp < last_cp` не даёт выйти за последний, а обратный ход невозможен, потому что проверяется всегда только следующий по счёту.

### Три способа умереть

| Причина | Условие |
|---|---|
| врезалась | значение поля в точке машинки меньше половины ширины кузова |
| застоялась | `idle >= IDLE_LIMIT`, то есть 300 шагов без нового чекпоинта |
| финишировала | взяты все чекпоинты |

Финиш тоже снимает машинку с трассы, но перед этим записывается номер шага в `finish_step`. Так поколение не ждёт финишировавших, а те, кто ещё едет, доезжают.

Проверка столкновения через поле бесплатна: значение уже посчитано для всей сетки, остаётся сравнить его с половиной ширины кузова. Габариты кузова и его пересечение со стенами считать не надо.

Простой убивает стратегию "ехать медленно по кругу в одном месте". Без него машинка, нашедшая безопасный пятачок, крутилась бы там все 1800 шагов и мешала бы отбору, занимая место в популяции.

## Приспособленность

```
score = (взятые_чекпоинты + доля_до_следующего) * 100
      + если финишировала: (1800 - шаг_финиша) * 0.5
```

Целая часть даёт грубый прогресс, дробная сглаживает его между чекпоинтами.

**Зачем дробная часть.** Без неё приспособленность растёт ступеньками по 100. Внутри одной ступеньки все машинки неотличимы, и отбор между ними случаен. А в начале обучения все как раз находятся внутри первой ступеньки, и эволюция стартует вслепую.

Доля считается проекцией: вектор от текущего чекпоинта до машинки проецируется на вектор до следующего чекпоинта и делится на его длину. Результат обрезается в `[0, 1]`. Тест `test_fitness_grows_smoothly_between_checkpoints` проверяет монотонный рост.

**Про бонус за финиш.** Он равен количеству сэкономленных шагов, умноженному на 0.5. Максимум около 900, то есть девять чекпоинтов. Этого достаточно, чтобы среди финишировавших отбирались быстрые, но недостаточно, чтобы быстрый недоезд победил медленный финиш.

**Почему именно чекпоинты, а не пройденное расстояние.** Расстояние легко накрутить, крутясь на месте. Расстояние по прямой от старта максимально на противоположной стороне трассы и потом начинает убывать. Чекпоинты измеряют ровно то, что нужно: продвижение вдоль трассы в правильную сторону.

Это ровно тот случай, который в больших моделях называют reward hacking: агент оптимизирует написанную метрику, а не задуманную. Функция приспособленности здесь самое хрупкое место проекта, куда более хрупкое, чем сама сеть.

## Свойства и функции

| Имя | Что даёт |
|---|---|
| `done` | все мертвы или кончились шаги |
| `n_alive` | сколько ещё едет |
| `n_finished` | сколько доехало |
| `leader` | номер машинки с лучшей приспособленностью |
| `run(trk, fld, veh, brains)` | прогнать заезд до конца и вернуть `Race` |

```python
import numpy as np
import brain, car, field, race, track

trk = track.evolve_track(np.random.default_rng(0))
fld = field.build_for_track(trk)
veh = car.random_car(np.random.default_rng(0))
brains = np.random.default_rng(0).normal(0, 1.0, (50, brain.genome_size()))

r = race.run(trk, fld, veh, brains)
print(r.steps, r.n_finished, r.cp.max(), round(float(r.fitness().max()), 1))
```

`run` используется в `train.py` для расчёта без графики. В `main.py` заезд идёт по шагам вручную, чтобы между шагами рисовать кадр.

## Связи

Берёт трассу и чекпоинты из `track.py`, поле из `field.py`, параметры машинки из `car.py`, датчики из `sensors.py`, сеть из `brain.py`.

Отдаёт приспособленность в `train.py`, который передаёт её в `evolution.py`.

`render.py` читает `pos`, `angle`, `alive` и `leader` для отрисовки.
