# field.py

Поле расстояний до стен. Сетка, где в каждой клетке лежит одно число: насколько эта точка внутри трассы.

Положительное значение означает "внутри полотна, и до ближайшей стены столько пикселей". Отрицательное означает "снаружи, и на столько пикселей мимо". Ноль это ровно стена.

## Зачем это нужно

Ради скорости.

В лоб датчики считались бы так: у каждой из 50 машинок 7 лучей, каждый луч надо пересечь с каждым отрезком стены, а отрезков 720 (по 360 на стену). Получается 252 тысячи проверок пересечения на один шаг физики. Шагов в поколении 1800. Итого 450 миллионов проверок на поколение, и это только датчики.

Столько Python не потянет даже с numpy.

Поле расстояний переворачивает задачу. Один раз на трассу строится сетка, дальше луч не пересекает ничего, а просто идёт вдоль своего направления и смотрит значения в клетках. Обращение к элементу массива вместо решения системы уравнений.

Стоимость: около 0.2 секунды на построение поля, один раз на трассу. Взамен датчики становятся 11 тысячами обращений к массиву на шаг вместо 252 тысяч пересечений, и всё это одной операцией numpy без циклов.

Бонусом та же сетка бесплатно решает вторую задачу: столкновение. Машинка мертва, если значение поля в её точке меньше половины ширины кузова. Габариты и пересечения кузова со стенами считать не надо.

## Как считается значение

Трасса это труба постоянной ширины вокруг центральной линии. Значит расстояние от точки до стены выражается через расстояние до центральной линии:

```
значение = половина_ширины - расстояние_до_ближайшей_точки_центральной_линии
```

Расстояние до линии приближается расстоянием до ближайшей из 360 её точек. При длине круга около 2000 пикселей соседние точки стоят примерно через 6 пикселей, и погрешность такого приближения выходит меньше пикселя. При размере клетки 6 это в пределах шума.

Такой приём работает именно потому, что трасса имеет постоянную ширину. Для произвольного многоугольника пришлось бы считать расстояние до отрезков, а не до вершин.

## Функции

### `build(center, half_width, cell, pad) -> Field`

Строит поле. `center` это `(N, 2)` центральная линия, `half_width` половина ширины полотна.

Границы сетки берутся по габаритам линии плюс `half_width` плюс `pad`. Значение в клетке считается для её центра, отсюда сдвиг на `+0.5` при построении координат.

**Про разбиение на куски.** Расстояние считается матрицей "клетки на точки линии". Для типичной трассы сетка выходит около 120 на 120, то есть 14 тысяч клеток, умножить на 360 точек, умножить на 2 координаты, умножить на 8 байт это порядка 80 мегабайт единовременно. Плюс столько же на промежуточный результат возведения в квадрат.

Поэтому клетки обрабатываются кусками по `FIELD_CHUNK = 4096`. Скорость почти та же, пик памяти падает до пары мегабайт.

Свёртка квадратов сделана через `np.einsum("cpk,cpk->cp", diff, diff)`, а не через `np.linalg.norm`. Разница в том, что `einsum` не создаёт лишних промежуточных массивов.

### `build_for_track(trk, cell, pad) -> Field`

То же самое, но берёт линию и полуширину прямо из объекта `Track`. Обычный способ вызова.

### `Field.sample(pts) -> ndarray`

Значения поля в точках. Принимает массив любой формы `(..., 2)`, возвращает массив формы `(...)`, то есть без последней оси.

Это важно для `sensors.py`: туда приходит массив проб формы `(машинки, лучи, пробы, 2)` и должен вернуться `(машинки, лучи, пробы)`.

Точки вне сетки возвращают `OUTSIDE = -1e6`. Такое значение выбрано, чтобы оно всегда читалось как "глубоко снаружи" и любая проверка `< 0` или `< половина_кузова` срабатывала.

Индекс клетки берётся через `np.floor`, а не через приведение к `int`. Приведение к `int` в Python и numpy отбрасывает дробную часть в сторону нуля, то есть `-0.7` превращается в `0`, а не в `-1`. Для координат левее начала сетки это дало бы неверную клетку. `np.floor` округляет вниз всегда.

```python
import numpy as np
import field
import track

trk = track.evolve_track(np.random.default_rng(0))
f = field.build_for_track(trk)

print(f.sample(trk.center[:3]))   # около 45, это половина ширины
print(f.sample(trk.left[:3]))     # около 0, это стена
print(f.sample(np.array([[1e6, 1e6]])))  # -1e6, вне сетки
```

## Про запас вокруг трассы

`FIELD_PAD = 80` может показаться мало: дальность луча 256 пикселей, а запас всего 80.

Противоречия нет. Луч ищет первую пробу с отрицательным значением, то есть первую точку за стеной. Стена стоит на расстоянии половины ширины от центральной линии, а сетка покрывает линию плюс полуширину плюс запас. Значит луч уходит за стену максимум на один шаг пробы, на 8 пикселей, и до края сетки не добирается никогда.

Запас 80 оставлен на габариты машинки и на то, чтобы отрисовка не упиралась в границу.

## Точность

Размер клетки 6 пикселей задаёт точность и столкновений, и датчиков. При ширине трассы 90 это примерно 7 процентов.

Уменьшение клетки вдвое учетверяет и память, и время построения поля. Увеличение экономит немного, но машинка начинает замечать стену с запозданием и врезаться там, где могла бы проехать.

Значение поля не интерполируется между клетками, берётся значение клетки целиком. Для игры этого достаточно, интерполяция стоила бы четырёх обращений вместо одного.

## Связи

`sensors.py` вызывает `sample` для проб вдоль лучей.

`race.py` вызывает `sample` для позиций машинок и по значению решает, кто врезался.

Строится один раз в `main.py` при смене трассы.
